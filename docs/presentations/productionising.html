Productionising the Shift Simulator

ORIGINAL/SHOWROOM-SHIFT-SIMULATOR.HTML -> PRODUCTION

From one HTML file
to a production app

How the London Paint Showroom Shift Simulator was ported to a tested React app by an unattended work loop

showroom-shift-simulator.vercel.app

This is the story of taking a single self-contained HTML game and turning it into a tested, continuously integrated React app running in production. Most of the code was written by an unattended work loop: headless agent sessions that each implemented one ticket. The interesting parts are the planning, the guard rails, and the three places where the loop got stuck.

THE STARTING POINT

One self-contained HTML file that worked as a demo

What it had

  • Pixel-art canvas game, two rounds
  • WebAudio sound effects and mute
  • Keyboard and touch controls
  • A clear business story

What it lacked

  • Any tests, or a way to write them
  • Speed tied to screen refresh rate
  • Mixer hum that could keep playing
  • Zoom disabled; no focus handling

The original was a single HTML file: CSS, markup and one script that mixed game rules, canvas drawing, audio and DOM updates. It worked well as a demo. But nothing could be tested without a browser, and the game advanced one step per animation frame, assuming 60 frames a second. On a 120 Hz screen the 30-second shift ran twice as fast. There were smaller defects too: the shaker hum could keep playing after a round ended or after muting, and the page blocked pinch zoom.

THE GOAL

Same game, same numbers, same look.
Built so it can be trusted.

A faithful port, not a redesign. The only behaviour change allowed: real-time timing, so a shift lasts 30 seconds on every screen.

We scoped the work deliberately narrow. No new gameplay, no rebalancing, no dark theme, no new visual style. Every tuning number, every line of copy and every pixel colour stays as the original had it, and the original file is kept in the repo as the approved design. That made acceptance easy to judge: does the port match the original, and is it now testable, accessible and independent of refresh rate.

HOW THE WORK RAN

An unattended loop: one ticket per agent session

Plan

Grill, decide, write tickets

Worker

Fresh session builds one ticket

Gates

Lint, types, tests, build

Verify

Check each criterion

Merge

Squash, next ticket

A supervisor session watches the event file, verifies from facts, and asks the owner before anything outside the repo: deploys, merges it is not cleared for, clearing a halt.

The build used forger, a work loop. Planning is interactive: the owner answers decisions in rounds, each with a recommendation. After that, an engine picks the next ticket and launches a fresh headless agent session to implement it end to end. The session must pass the gates, push, and open a PR. A verifier then checks each acceptance criterion against evidence before the merge. The supervisor never writes code. It starts the engine, watches for terminal events and reports back, and it escalates anything that needs the owner.

PLANNING

Decisions made before any code was written

DecisionChoice
FidelitySame mechanics, numbers, copy and pixel art
TimingFixed 1/60 s steps from real elapsed time; capped, frozen when hidden
Game logicPure, seeded functions with no DOM or audio
DesignThe original file is the approved design
AccessibilityZoom allowed, focus-trapped dialog, live dialogue, axe clean
StackVite, React 19, strict TypeScript, Vitest, Playwright, bun

Planning ran as two numbered rounds of questions, each with a recommended answer; the owner accepted all of them. The two architectural ones were recorded as ADRs in docs/adr: the pure simulation on a fixed timestep, and the original as the approved design. A glossary pinned down vocabulary such as shift, unmanned, walkout and hub dispatch, so tickets and tests use the same words.

ARCHITECTURE

Pure simulation in the middle, thin shells around it

Real-time loop

Accumulates elapsed time, runs whole steps

src/game

step(state, rng) returns the next state and events. Seeded, no DOM, no Math.random

Canvas renderer

Audio engine

React HUD

A whole two-round shift can be replayed in a unit test, step for step.

All game rules live in src/game as pure functions: state in, state out, plus a list of events such as chime, walkout or hum start. Randomness comes from an injected seeded generator, so tests replay exactly. The browser loop accumulates real time and runs as many fixed 1/60 second steps as fit, capped at 250 ms per frame and frozen while the tab is hidden. The canvas, audio and React only read state or consume events. A purity test fails the build if src/game ever imports React, the DOM or audio.

Each ticket was sized for one fresh agent session and carried testable acceptance criteria, file hints and the pattern to reuse. Dependencies made the order mechanical. Once the loop was unblocked, canvas-render through sound merged back to back; each worker session took between about three and six minutes.

SNAG 1 OF 3 - AFTER TICKET 1

The work was done, but the loop could not see the repo

Symptom

Scaffold was pushed and its PR opened, then the loop halted: completed, nothing merged. Git pushed over SSH, but the GitHub CLI was signed in as a second account that could not see the private repo.

Fix

Merge the finished PR by hand, then restart the engine with the repo owner's token in its own environment only. The global login was left alone.

The loop halted on purpose: a ticket marked completed with nothing merged is not done, so it stopped instead of re-running the work. The cause was identity. Two GitHub accounts were signed in and the active one could not resolve the repository. The lesson is to give the loop a scoped identity of its own rather than rely on whichever account is active.

SNAG 2 OF 3 - AFTER TICKET 2

The verifier only understood issue-numbered branches

Symptom

With a local backlog, branches were named feat/sim-core. Verify expects feat/issue-n, so it could not name the ticket, and merge refused without a verdict. Every ticket would halt the same way.

Fix

Switch the tracker to GitHub Issues by PR: remaining tickets filed as issues #3 to #7 with labels and native blocked-by links. Branches became feat/issue-n.

This one was a defect in the loop tooling, not in the app. The worker diagnosed it itself, pointed at the line in the verifier, and stopped rather than merge unverified. The fastest route was to move the backlog onto GitHub Issues, which the verifier fully supports. Right after the switch, four tickets merged in a row with no human involvement. The verifier bug is still worth fixing upstream for other local-backlog repos.

SNAG 3 OF 3 - THE LAST TICKET

"It passes on my machine" is not evidence

Symptom

The e2e and accessibility ticket passed locally, but the verifier could not use browser tests as evidence. After three rounds it handed the PR to the owner, who spotted the real gap: no CI.

Fix

PR #15 added GitHub Actions: gates plus Playwright and axe on every PR. PR #14 was rebased onto it, went green in CI, and both were merged.

Until this point every "all green" claim came from a worker's own machine. The owner, reading PR 14, asked the right question: where does this run where anyone can see it. The CI workflow runs bun run gates and the full Playwright suite, including axe, on every pull request and on pushes to main. Along the way axe found real contrast failures in the round modal's coloured text, and the worker fixed them with darker tokens.

WHAT SHIPPED

Live on Vercel, guarded by CI

Production

The React build from main, at showroom-shift-simulator.vercel.app

CI

Gates and e2e with axe on every PR and every push to main

Rollback

The original page stays in deployment history and in original/

The playable original went to production first, as a stop-gap while the port finished. Once PR 14 merged and CI was green on main, a fresh build from main replaced it. The original remains in Vercel's deployment history for an instant rollback, and in the repo as the reference design.

LESSONS

What we would do the same, and differently

Keep: decide before building

Two rounds of planning questions gave workers tickets they could finish cold.

Keep: pure core, thin shells

Seeded logic made every rule testable without a browser.

Change: CI on day one

Shared, visible checks should come with the scaffold, not the last ticket.

Change: check the plumbing first

Remote, identity and tracker should be proven with one dry run.

Two things clearly worked: planning decisions up front, and isolating the game rules as pure, seeded code. Two things cost us halts: CI arrived last instead of first, and the loop's plumbing, meaning the git remote, the GitHub identity and the tracker type, was not proven before the first real ticket. A single dry-run ticket would have surfaced both snag 1 and snag 2 in minutes.

NEXT STEPS

Make the guard rails mandatory

  1. Require the CI checks on main in branch protection
  2. Fix the verifier upstream: local branch names, browser-test evidence
  3. Play-test production on a real phone

Today GitHub would still allow a merge with failing checks, because nothing is required on main. Requiring the two CI jobs, and optionally the loop's own verify check, closes that gap. The two verifier fixes belong in the forger tool so the next repo does not hit the same halts. And automated checks are not a substitute for someone actually playing a round on a phone.
