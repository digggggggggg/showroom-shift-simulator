Forger in Five

FORGER

Tools decide.
Models judge.
Software ships.

An unattended development loop that lets any model forge ahead reliably

Forger is a work loop for building software with AI agents unattended. Its one big idea: anything that must come out the same every time is a tested command the model cannot talk its way around. The model only reasons where judgement is needed, between hard boundaries the tools enforce. I'll show the goals in one slide, then use a real project, the Shift Simulator, as proof.

THE GOALS

Determinism first

Picking work, gating, merging and measuring are tested commands. Any model, any harness.

Verify, never trust

One ticket, one worker, one PR. Done means merged with green checks, not "I finished".

The owner decides

Agents recommend. Halts, deploys and anything outside the repo wait for a person.

It learns

Every correction climbs from a note to a rule, a check and finally a tool.

Four goals, all from forger's principles. One: determinism first. Selecting the next ticket, running the gates, deciding whether a ticket merged, measuring the process: those are commands with JSON output, so the model and the harness are interchangeable. Two: verify, never trust. A worker's claim is not evidence; a merged PR with passing checks is. Three: the owner decides, everyone else recommends, through an explicit approval table. Four: the process refines itself, so a lesson learned once holds without anyone having to remember it.

The Shift Simulator started as a single self-contained HTML game. Forger planned it into seven vertical slices after two short rounds of questions, then fresh agent sessions built each one: pure seeded game logic, the canvas, the controls, the modals, sound, and keyboard plus accessibility tests. The owner's job was decisions, not code: approving the plan, unblocking halts, asking for CI, approving the deploy. Four tickets landed back to back in about nineteen minutes once the plumbing was right.

This is the slide that matters. Each time something broke, forger stopped rather than march past work it could not verify. A ticket marked done with nothing merged halted the loop. A PR with no verdict was not merged. A criterion the verifier could not prove went to a human instead of being waved through. None of those halts were model failures; they were plumbing and tooling gaps, and the tools caught all three.

WHAT COMES NEXT

Every halt becomes a check, so the next project never hits it.

Local-branch verify, browser-test evidence, CI in the scaffold, a plumbing dry run: four lessons climbing the ladder now.

Close on the self-improving loop. The three snags from this project are already lessons with a clear destination: the verifier should resolve local-tracker branch names and accept CI browser-test results as evidence; the scaffold should ship CI on day one; and setup should prove the remote, identity and tracker with one dry-run ticket. Once those are tools, the next project of this kind runs end to end without a single halt.
